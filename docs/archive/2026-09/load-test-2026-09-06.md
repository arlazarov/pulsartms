# Isolated load measurements — 2026-09-06

Production and live data were not modified. No external API providers or production
configuration were loaded. Runtime application code was not changed by these tests.

## HTTP Dispatch board

Run `dotnet run --project tools/LoadProbe/LoadProbe.csproj -c Release -- --sustained`.
Raw measured output: `load-probe-2026-09-06.jsonl` alongside this report.

The harness starts Kestrel on a random loopback port and executes the production
`GetDispatchBoardHandler`, `ReadCache`, EF projection and JSON response. Each fleet
has two active loads and four stops per truck. A separate, private in-memory SQLite
database is used. Requests alternate page browsing and equipment-prefix searching.
HOS, identity middleware, PostgreSQL/network latency, background synchronization and
fuel/route calculation endpoints are excluded. Client and server share one process
on the Mac; CPU, allocated bytes and working set include both.

Cold waves invalidate the board cache before simultaneous requests. Warm short
bursts run ten requests per worker. The 1,000-truck/20-worker case runs continuously
for 30 seconds, guarded by a 2 GB working-set limit. These are closed-loop workers
with no think time, **not a realistic dispatcher activity model**. Short-burst RPS
and cold-wave percentiles must not be used as sustained capacity guarantees.

| Trucks | Parallel workers | Warm p95 | Cold-wave p95 |
| ---: | ---: | ---: | ---: |
| 100 | 20 | 20.2 ms | 59.7 ms |
| 300 | 20 | 39.2 ms | 116.9 ms |
| 1,000 | 20 | 45.2 ms (30 s run) | 126.6 ms |
| 1,000 | 100 | 170.9 ms (short burst) | 517.6 ms |

Recorded run: **35,074 HTTP requests, zero HTTP failures**. The sustained case
completed 29,499 requests in 30.008 s, about 983 requests/s locally; p50 17.25 ms,
p95 45.24 ms, p99 64.05 ms, maximum 132.56 ms. This is a scenario measurement,
not a claim that the deployed service sustains this throughput.

### Allocation pressure

Warm requests allocate approximately 0.65 MB at 100 trucks, 1.35 MB at 300 trucks,
and **3.73 MB at 1,000 trucks**, while responses average about 39 KB. The sustained
case allocated 110.15 GB cumulatively, not simultaneously. One SQL details query
per warm request was observed; cold waves added two index queries, rather than
loading the index independently for every worker.

Code inspection supports a likely cause: the board's cached full-fleet index is
deserialized in `ReadCache.Restore` before filtering/pagination. Exact allocation
attribution still requires an allocation profile; these totals alone do not assign
every byte to that method.

At the end of the 1,000-truck suite, forced GC left approximately 57.1 MB of managed
memory while process working set remained about 1.71 GB. This distinction matters:
allocation churn and reserved/runtime memory are not equivalent to a retained-object
leak. A 30-second test does not rule out longer-term leaks.

## Real WebGL fleet layer

Build `tools/MapLoadProbe/probe.js` with the client's esbuild, outputting
`tools/MapLoadProbe/probe.bundle.js`. Serve that folder on loopback, open `index.html`
in the foreground, and click Run. The fixture uses the current `createScene` and
real deck.gl layers, replacing only GoogleMapsOverlay with a standalone Deck host.

Hardware observed: **Apple M3 Pro, ANGLE Metal**, 2× device pixel ratio, fixed
1,000×600 CSS-pixel canvas. Four scenarios: 30, 100, 300 and 1,000 moving trucks,
2,000 stations, a 2,000-point route and two stop labels. Each has 2.5 seconds warmup
and 12 seconds of motion, scripted camera zoom/pan, periodic picking and label updates.

First pass, without explicit GPU timing queries: all four scenarios recorded
720–721 animation callbacks in approximately 12 seconds. Frame-interval p95 was
17.1–17.6 ms; none exceeded 33.34 ms and no long tasks were observed. These are
browser callback intervals, not direct proof of screen presentation frequency.

Second pass enabled non-blocking `EXT_disjoint_timer_query_webgl2` queries around
the Deck draw pass, sampling every tenth draw and discarding disjoint results.
Each scenario completed 720 draw callbacks and produced 72 GPU samples. Camera
updates and picking were the same as the first pass. No frame intervals over
33.34 ms or long tasks were observed in this pass either.

| Trucks | Frame interval p95 | GPU draw p50 | GPU draw p95 |
| ---: | ---: | ---: | ---: |
| 30 | 18.5 ms | 1.20 ms | 7.91 ms |
| 100 | 18.3 ms | 1.32 ms | 3.39 ms |
| 300 | 18.6 ms | 1.47 ms | 3.25 ms |
| 1,000 | 17.7 ms | 2.03 ms | 8.66 ms |

The non-monotonic GPU tails and small sample count mean these are observations,
not stable capacity limits. GPU draw duration is not GPU utilization percentage,
and does not include Google's basemap or prove display presentation timing.

This excludes Google's basemap, Blazor, live traffic, network/telemetry, DOM detail
cards and physical trackpad input. The phone and a multi-hour soak remain untested.
GPU memory statistics were unavailable (the library returned zero); zero is not
reported as actual GPU memory usage.

## Interpretation

The tested fleet layer has useful rendering headroom on this Mac. The most concrete
server scaling concern found is board allocation pressure, not an HTTP failure or
an immediate latency collapse. Next measurements should target allocation stacks,
an isolated PostgreSQL environment with the full application pipeline, the complete
Google map on mobile, and a longer-duration soak. No whole-product capacity claim
or before/after FPS improvement is established by these fixtures.

## Dispatch index fix and repeat measurement

The board now caches a `DispatchBoardIndex` with private immutable search data.
Mutable page DTOs are constructed only for selected rows; details and HOS still
load through the existing request path. The cache retains its generation/TTL,
32 MB total bound and 8 MB per-entry limit with conservative snapshot accounting.
Other cached response types still use their previous cloning behavior.

Same harness, fixture and Release configuration, 1,000 trucks / 20 closed-loop
clients / 30 seconds. Raw repeat output: `load-probe-after-2026-09-06.jsonl`.

| Metric | Before | After |
| --- | ---: | ---: |
| Allocated bytes per request, combined process | 3,733,897 | 319,928 |
| Response p95 | 45.24 ms | 10.20 ms |
| Response p99 | 64.05 ms | 12.52 ms |
| Requests/s, local stand | 983 | 2,717 |
| Working set at end of sustained case | 1.659 GB | 0.288 GB |

Per-request allocation fell 91.4%. p95 was 77.5% lower in this repeat, but timings
and working set are observations of two separate runs, not controlled production
capacity guarantees. The response payload and warm SQL query count remain similar.
Across the repeat's scenarios: 87,084 HTTP requests, zero HTTP failures.

249 tests passed, including new coverage for input/response mutation isolation,
search and ordering, concurrent cache reuse, invalidation, oversized entries,
fresh database details and page allocation independent of total fleet size.
