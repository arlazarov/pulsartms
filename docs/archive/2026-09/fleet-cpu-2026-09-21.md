# Native fleet CPU measurement

Measured the existing native ARM64 50-truck fixture using deltas from
`/sys/fs/cgroup/cpu.stat`. CPU percentage is CPU seconds divided by wall
seconds, with 100% representing the configured one-CPU quota. No builds or
tests ran concurrently. The ordinary browser remained open, so its polling
and background work are included in container totals.

| Phase | Wall seconds | CPU seconds | Average CPU | Throttled seconds |
| --- | ---: | ---: | ---: | ---: |
| Idle | 20.01 | 0.18 | 0.9% | 0.00 |
| 15 planning reads, concurrency 5 | 8.29 | 4.34 | 52.4% | 0.44 |
| 15 Dispatch reads, concurrency 5 | 12.94 | 2.75 | 21.3% | 0.00 |
| Enqueue and drain 50 truck updates | 188.30 | 31.02 | 16.5% | 0.33 |
| One fuel and ETA calculation | 10.44 | 1.51 | 14.5% | 0.06 |

All requested operations completed successfully. The queue drained to zero,
with zero reported retries. The fuel operation produced two stops and two
populated forecasts. Route provider call counts stayed at 200 during the
queue pass: this exercised updating existing saved routes, not fetching 50
new roads. No forced GC or production changes were made.

## Interpretation

The earlier suggestion that one CPU was insufficient to explain queue delay
was not established by the memory experiment. This direct measurement shows
low average CPU utilization during the slow queue pass and little throttling.
Adding CPU is not justified as the primary solution for this scenario.

Time outside CPU execution includes asynchronous I/O, scheduling and waits.
The remote PostgreSQL fixture and sequential awaited persistence/service
operations are investigation targets, not measured attribution of all delay.
These counters do not identify individual CPU stacks or prove which SQL query
is slow. They also do not establish production capacity: providers remain
synthetic and network distance to the database differs from deployment.

Next useful measurement is request/job tracing with database query counts and
durations, separating connection waits, SQL round trips and application
execution. Do not increase concurrency blindly; database pressure and memory
must be measured alongside any change.
