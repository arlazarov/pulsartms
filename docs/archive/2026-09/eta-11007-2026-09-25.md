# Truck 11007: map ETA dash while Dispatch shows it (open)

**Reported** by the owner around 22:42 Toronto on September 24 (02:42 UTC
September 25). The Fleet Map showed "—" for the ETA of truck 11007
(`18dd87c9-…`). At the same time, Dispatch details for AMF1386
(`c4cdc5b2-…`) showed "Sep 25 12:28 PM On time". The pickup was done, the
next stop was the delivery at Target DC #3802 in Amsterdam, NY, with 206
miles remaining and hours of service visible.

**Status:** root cause not proven. No guard was changed and no fix was
made. Nothing was written to production. Everything below was read with
bounded `READ ONLY` queries and Cloud Run logs.

## What production held (03:10 to 03:23 UTC)

- **Load:** AMF1386 `in_transit` on the truck, with one active execution
  leg (`fab6afca-…`, revision 10).
- **Saved plan:** version 15, from the truck's position, `inputsChanged`
  false. Next stop is the delivery (`ace6e8a6-…`), with no passed stops in
  the plan (it holds only the remaining stop). Its reference stops are the
  same delivery, with no `referenceSource`, written by the pre-release
  binary. Calculated at 17:45 UTC.
- **Persisted forecast:** for the same load, leg and assignment revision,
  its first stop is the delivery. It is not pending and is valid for 2
  minutes.
- **Recalculation rate:** sampled every 15 seconds for 3 minutes, the
  forecast was recalculated at 03:20:32, 03:21:04, 03:21:33, 03:21:43,
  03:22:13 and 03:22:51. That is every 10–40 seconds, not the 2-minute
  refresh.
- **Map traffic:** two map views polled
  `POST /api/fleet/trucks/18dd87c9…/planning` about every 10 seconds, with
  `next-routes` every 20 seconds. One instance served everything, and no
  request failed.

## Ruled out, with evidence

- **The plan's inputs changed:** stored `inputsChanged` false, next stop
  consistent, and no recalculation since 17:45.
- **The display snapshot changes the plan's stops or tracking:** the real
  plan JSON (read-only, kept only in the session scratchpad) reads
  identically through `RoutePlanStorage` and `RouteDisplayCache`
  (display and known-version forms).
- **The map and the worker describe the load differently:** in the ETA
  chain fixture, with names, notes, commodity and appointment time zones
  filled, the two loads serialise identically, and the map's display read
  finds the worker's forecast as current. Kept as
  `EtaChainInputTests.TheMapReadFindsTheForecastTheWorkerMade`.
- **Telemetry disagreement in the route key:** with server telemetry sync
  on, both reads take positions from the same snapshot.
- **A second instance without the forecast in memory:** one instance
  served all of it.
- **A stuck Client refresh flag:** it is set per poll and cleared on
  every successful answer.

## What would produce exactly this, not yet shown

The map's ETA comes from the ETA worker's memory in the API process
(`EtaService.GetCached`). Dispatch's ETA comes from the persisted forecast
it matches against a fresh chain description (`EtaForecastService`).

Two paths make the memory answer empty for the map while the persisted
forecast stays valid:
- a read that judges the entry to be other work (`RemoveIfCurrent`);
- a Dispatch read whose chain input hash differs from the one the entry
  was published with (`EtaMemory.Demand`).

Each asks the worker for a refresh, which fits the recalculation rate
above. On the Client, an answer without an ETA keeps the last forecast and
drops it 15 minutes after that forecast's `ValidUntil`
(`FleetRouteDisplayMemory`). Only a run of empty answers longer than that
gives a lasting dash.

Why the chain input hash, or the work, would differ for this truck is
not shown. The chain hash includes the itinerary's input signature, the
driver, deadhead history, the root road versions and the planning
options.

## Instrumentation (counters, no behaviour change)

Instead of a log line per poll, each map read and each removal is counted
in the admin-only `GET /api/diagnostics/stages`, per API process since it
started (`items`):

- `eta-map-read/current` and `eta-map-read/updating`: a forecast shown,
  current or marked as updating;
- `eta-map-read/no-entry`: nothing kept for the load;
- `eta-map-read/other-work`, with `other-work-TruckId`, `-DispatchId`,
  `-ExecutionLegId`, `-AssignmentRevision` or `-Stops` naming what differs
  from the work the forecast was kept for;
- `eta-memory/demand-removed`: taken back because a Dispatch read
  described the chain differently;
- `eta-memory/unsaved-removed`: published, then not saved, and taken back.

The counters are fleet-wide, not per truck. Read twice a minute apart
while only the 11007 map is open: a rising `no-entry` with
`demand-removed` points to the chain description; a rising
`other-work-*` names the part of the work the map and the worker see
differently. Released with the September 25 package; not yet read in
production.

## Recurrence and 11005 (September 25, 11:58–12:01 UTC, read only)

The owner saw 11007 (AMF1386, 141 mi) with a dash again, after it had
shown an ETA earlier: the dash was transient, not fixed. 11005 (AMF1403,
truck `055c8fd9-…`) shows the same dash. Six reads of
`DispatchEtaForecasts`, 20 seconds apart, found:

- **11007**, current leg (assignment revision 10): the input hash stayed
  `5E839328` throughout. The forecast was saved again at 11:58:21,
  11:58:59, 11:59:12, 11:59:38, 12:00:08 and 12:00:22, each with 1 stop,
  not pending, and valid for 2 minutes.
- **11005**, current and next leg (revisions 7 and 2): the input hash
  stayed `C78FF3DD`, and both were saved again about every 30 seconds.
- **Requests in the same 3 minutes:** 2 `POST /api/fleet/trucks/{id}/planning`
  and 1 board planning read. The map was not polling every 10 seconds.

**What this rules out and shows:**
- **Chain drift:** ruled out. The hash never changed, so a Dispatch or
  board read describing the chain differently (`EtaMemory.Demand`) is not
  the cause.
- **A merely superseded forecast:** ruled out. It would be returned from
  the worker's cache while still valid, not recalculated.
- **What is happening:** each recalculation means the in-memory forecast
  was deleted.
- **The likely caller:** the background planning summary. It prepares
  running trucks about every 30 seconds whether or not a page is open,
  and calls `EtaService.GetCached`. `GetCached` deletes a forecast it
  judges to be for "other work", meaning the forecast's `WorkKey` (truck,
  load, leg, assignment revision, stops) differs from the summary's.
- The worker then rebuilds the forecast, and the next summary deletes it
  again, so the map, which reads the summary, gets no ETA.

**Not yet shown:** which part of `WorkKey` differs. The deployed counters
name it. Two reads of `GET /api/diagnostics/stages` (admin), a minute
apart, will show which `eta-map-read/other-work-<Part>` rises. No guard
was changed.
