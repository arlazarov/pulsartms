# Dense-route local fleet load test

The user stopped escalation after 50 trucks. No 100-truck run was started.
No production configuration or memory limit was changed.

## Fixture and limitations

The real API, authentication, Application services, route queue and PostgreSQL
persistence ran in Linux x64 under Docker emulation on an ARM Mac, with one CPU,
1 GiB memory and no swap. PostgreSQL was an existing isolated remote fixture;
no database server was started locally or in a container. The fixture applied
existing migrations in its own schema.

Routing and HOS providers were synthetic. Each truck had two accepted loads,
with an approximately 3,830 km first route sampled at approximately 50 m,
including synthetic bends (roughly 75,000 input vertices). Roads are not
navigable. Provider network parsing and ordinary import/background workloads
were excluded. Fuel and ETA were explicitly calculated through real services.
The actual two-consumer planning worker processed telemetry refresh requests.
Five independently authenticated dispatchers read locations, plans and boards.
The runtime reported workstation GC, not server GC. Emulation and the remote
database prevent direct production latency or capacity conclusions.

## Results

All 50 trucks received saved routes and fuel plans, with 100 populated ETA
forecasts. All 287 measured requests succeeded. The queue drained to zero;
no retry counts above one were observed. No 100-truck capacity claim is made.

| Phase | Observed peak container MiB | Approximate duration |
| --- | ---: | ---: |
| Baseline | 260 | Initial sample |
| Cold preparation, concurrency 2 | 852 | 666 seconds sampled |
| Five dispatchers and telemetry | 926 | 187 seconds sampled |
| Queue drain | 885 | 113 seconds sampled |
| Idle, no forced GC | 853 | 119 seconds sampled |

Final container usage was approximately 777 MiB. The observed peak left only
98 MiB below the configured limit. Three-second samples can miss shorter peaks.

| Operation | Count | Median ms | Sample p95 ms |
| --- | ---: | ---: | ---: |
| Prepare route, fuel and ETA | 50 | 23,707 | 43,012 |
| Truck planning read | 75 | 3,086 | 4,877 |
| Dispatch board read | 75 | 4,044 | 5,398 |
| Fleet locations read | 75 | 14 | 160 |

The all-truck refresh cycle did not keep up with a new request version every
30 seconds. Requests coalesced and eventually completed after demand stopped.

## Memory evidence and next investigation

Cold preparation allocated about 172.65 GiB cumulatively; steady activity
allocated another 14.80 GiB and queue drain 9.83 GiB. These are cumulative
allocation counters, not simultaneous RAM occupancy. At the final sample,
managed objects were estimated at 118 MiB, fragmentation after the most recent
GC at 139 MiB, and GC committed memory at 285 MiB. Known byte-accounted caches
were approximately 42 MiB. These figures overlap and must not be added.

This is evidence of allocation pressure and retained process memory, not proof
of a managed leak. Investigate allocations in route reconstruction, geometry
copies and serialization, and allocation call stacks before changing cache
limits or retaining less business data. The memory map also includes executable
anonymous mappings under emulation; its categories do not identify owners.

## Verification and evidence

Before the 50-truck run, all 4,853 automated tests passed (3,176 server,
1,052 Client C#, 625 JavaScript), along with JavaScript type checks. The probe
Release publish, CSharpier check, Python compilation and git diff check passed.
The ten-truck calibration was checked in the actual browser: route drawing,
truck selection, ETA and saved fuel stops. A separate 50-truck browser check
was not performed; the user stopped escalation before the intended 100-truck
browser pass. HTTP success does not establish browser responsiveness.
